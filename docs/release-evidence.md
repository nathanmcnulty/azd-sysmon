# Promotion and release evidence

This checklist defines a future qualification review; completing this document
is not live acceptance or release authorization. Select the exact candidate,
features, account, tenant, subscription and disposable targets before running
any deployment or cleanup command. Disabled features need no extra permission.

## Promotion checklist

- [ ] Freeze the Git revision, tree and diff for independent review. Record Git
  blob object IDs, SHA-256 of raw indexed file bytes, and SHA-256 of raw working
  file bytes separately; record any line-ending normalization.
- [ ] From the solution root, run `pwsh -File ./scripts/Test-Repository.ps1`.
  Record tool versions, exit code and complete sanitized output. This validates
  offline source and mocked contracts, not live services or endpoint state.
- [ ] In two clean copies of the same pinned inputs, run
  `pwsh -File ./scripts/Build-SysmonPackages.ps1`. Compare every generated byte
  and `config/generated-package-manifest.json`; require no unexplained diff.
- [ ] For AMA, run `pwsh -File ./scripts/Build-AmaPackage.ps1 -MsiPath '<private-msi>' -OutputDirectory '<private-output>'`.
  Verify the MSI hash, signature, product code/version and publisher against
  `config/ama-client-release.json`; keep the binary and package privately.
- [ ] Verify `azd-components.lock.json` and every managed-file hash against its
  immutable source revision. The solution remains independently deployable.
- [ ] Review `LICENSE`, `THIRD-PARTY-NOTICES.md`, pinned upstream sources and
  their notices, generated attribution, and relevant release notes.
- [ ] Review [identity and authentication](identity-and-authentication.md) and
  the selected scripts. There is no canonical permission manifest on this
  revision. Intune declares `DeviceManagementScripts.ReadWrite.All` and, for
  AMA apps, `DeviceManagementApps.ReadWrite.All`; Defender declares
  `Library.Manage`. Review Azure deployment/VM permissions, Intune RBAC and
  licensing, and pre-existing `Monitored Objects Contributor` for client AMA.
  Record unknown requirements and effective-grant gaps. This is not consent,
  approval to grant a permission, or a claim of least privilege.
- [ ] Complete the selected rows below against this candidate. Record target
  class, exact command/query, timestamp, sanitized input/output hashes,
  observed result, limitations, and cleanup result or reason it was not run.
- [ ] Review README/operations/validation links, action SHAs, catalog display
  metadata, public repository metadata and review settings. Required checks,
  catalog enforcement, tags and releases retain their separate approval gates.
- [ ] Name the rollback owner. Review receipt-bound cleanup before deployment;
  preserve adopted objects and unrelated resources. Separately authorize any
  assignment expansion, reboot, device execution or software removal.

## Private evidence and public summary

Retain only necessary private target identifiers, receipts, binaries and
sanitized provider responses. Never retain bearer tokens, Authorization headers,
passwords, client secrets or SAS URLs as evidence, even privately. Redact them
before writing output; avoid debug traces and transcripts containing credentials.
Hash retained sanitized output as such, not as an unchanged raw response.

Keep actual tenant/subscription/device/group/account identities and raw receipts
outside Git. Public summaries may contain the candidate revision, target class,
commands with placeholders, evidence timestamp, hashes, result and redacted
cleanup summary. A hash binds retained bytes; it does not prove execution,
installation, ingestion or a human-visible result. Use a fresh directory for
every retry and preserve failed evidence.

## Evidence required by path

| Path | Qualification evidence | Cleanup boundary |
| --- | --- | --- |
| Client-only | Supported endpoint; exact package/configuration hashes; execution result, Sysmon service/channel and a fresh benign event marker. | Record prior software state and rollback owner; software removal is separate. |
| Sentinel/DCR | Workspace/DCR/XPath readback; target-attributed fresh raw Event and separate Heartbeat; selected parser result and volume/privacy review. | Remove only owned DCR/associations; preserve the existing workspace. |
| Azure VM | Guest Run Command output and endpoint proof; AMA extension state, named association readback and fresh ingestion. CLI transport success is insufficient. | `azd down` does not uninstall Sysmon/AMA or delete the operator-owned VM. |
| Intune | Content version/file commit and assignment readbacks; remediation state; selected-device installation report and endpoint execution/ingestion. Assignment is not installation. | Exact receipt, marker and assignment ownership; preserve adopted objects. |
| Tenant-wide client AMA | Explicit tenant-wide approval; discovered API versions, monitored-object/association/DCR readbacks, and observed target-population ingestion. | Preserve the monitored object and unrelated associations; dangling acknowledgment is not removal success. |
| MDE Live Response | Library before/after publication and after cleanup; exact file/configuration hashes. Device execution needs separate authorization and evidence. | Receipt/name/ownership-bound deletion; library absence does not prove device rollback. |

The commands below are templates, not actions run by this documentation change.
Run repository helpers from the solution root. Supply private selected values;
never infer a target from a display name. Use an already authorized cached
WAM/browser/SDK session for that identity. If it is absent or mismatched, stop
and resolve it through the normal flow in the identity guide; do not add scopes
or change authentication merely to collect evidence.

## Client-only execution and endpoint proof

After separate authorization, use the generated installer on the selected
supported endpoint in an elevated session:

```powershell
pwsh -File ./deploy/azure-vm/Install-Sysmon.ps1 -Configuration balanced
Get-Service Sysmon64,Sysmon -ErrorAction SilentlyContinue
Get-WindowsOptionalFeature -Online -FeatureName Sysmon
Get-WinEvent -ListLog 'Microsoft-Windows-Sysmon/Operational'
Get-WinEvent -LogName 'Microsoft-Windows-Sysmon/Operational' -MaxEvents 5 |
    Select-Object TimeCreated, Id, ProviderName, Message
```

Record the selected configuration hash and a fresh harmless process marker,
with target attribution. Do not require an unsolicited reboot.

## Sentinel and Azure VM

After authorization, the existing VM helpers are:

```powershell
pwsh -File ./scripts/Deploy-AzureVmSysmon.ps1 -VmResourceIds '<vm-resource-id>' -Configuration balanced
pwsh -File ./scripts/Install-AzureVmAma.ps1 -VmResourceIds '<vm-resource-id>'
pwsh -File ./scripts/Associate-AzureVmDcr.ps1 -VmResourceIds '<vm-resource-id>' -DcrId '<dcr-resource-id>' -AssociationName '<owned-name>' -Action Ensure
```

Retain guest output and independently read back the selected extension and
association, recording the actual ARM API versions and identities used. These
helpers do not provide every service or guest-health observation. Follow
[operations](operations.md) for endpoint checks and cleanup ownership.
Run the following in the explicitly selected workspace, correlate the selected
host and marker privately, and record the exact time window:

```kusto
Event
| where EventLog =~ 'Microsoft-Windows-Sysmon/Operational'
| where Source =~ 'Microsoft-Windows-Sysmon'
| where TimeGenerated > ago(1h)
| project TimeGenerated, Computer, EventID, SourceComputerId, EventData
| order by TimeGenerated desc
```

```kusto
Heartbeat
| where TimeGenerated > ago(2h)
| summarize LastHeartbeat=max(TimeGenerated) by Computer, Category, SourceComputerId
```

Raw Event, Heartbeat, ASIM output and Defender timeline observations are separate
claims. Capture the exact selected parser query/result separately if claiming
parser compatibility; an empty parser result cannot replace raw ingestion proof.

## Intune publication and separate queries

After authorization, the existing publishers are:

```powershell
pwsh -File ./scripts/Build-AmaPackage.ps1 -MsiPath '<private-msi>' -OutputDirectory '<private-output>'
pwsh -File ./scripts/Deploy-IntuneAmaApplication.ps1 -GroupId '<group-guid>' -MsiPath '<private-msi>' -EnvironmentName '<environment>'
pwsh -File ./scripts/Deploy-IntuneRemediation.ps1 -GroupId '<group-guid>' -Configuration balanced -EnvironmentName '<environment>'
```

The helpers return summaries, not a complete evidence bundle. Independently
query the receipt-bound app and script using the selected authorized Graph
context. The following are separate GETs, not publisher output; replace private
variables with recorded IDs and verify `Get-MgContext` matches the selected
account and tenant before calling them:

```powershell
$graphContext = Get-MgContext
if ($null -eq $graphContext -or $graphContext.TenantId -ine $expectedTenantId -or
    $graphContext.Account -ine $expectedAccount) { throw 'Selected Graph context mismatch.' }
$appRoot = 'https://graph.microsoft.com/v1.0/deviceAppManagement/mobileApps'
$scriptRoot = 'https://graph.microsoft.com/beta/deviceManagement/deviceHealthScripts'
Invoke-MgGraphRequest -Method GET -OutputType PSObject -Uri "$appRoot/$appId" |
    Select-Object id, publishingState, committedContentVersion
Invoke-MgGraphRequest -Method GET -OutputType PSObject -Uri "$appRoot/$appId/assignments"
Invoke-MgGraphRequest -Method GET -OutputType PSObject -Uri "$appRoot/$appId/microsoft.graph.windowsMobileMSI/contentVersions"
Invoke-MgGraphRequest -Method GET -OutputType PSObject -Uri "$appRoot/$appId/microsoft.graph.windowsMobileMSI/contentVersions/$contentVersionId/files" |
    Select-Object -ExpandProperty value | Select-Object id, uploadState, isCommitted
Invoke-MgGraphRequest -Method GET -OutputType PSObject -Uri "$scriptRoot/$scriptId"
Invoke-MgGraphRequest -Method GET -OutputType PSObject -Uri "$scriptRoot/$scriptId/assignments"
```

Do not persist complete content-file responses: upload URLs can contain SAS
credentials. Capture only reviewed fields. Follow validated pagination when a
collection has more pages; one page is not complete inventory. Separately obtain
the current selected-device Intune installation/run report or portal export,
record its actual query/report identity, time, target and observed result, and
verify endpoint execution/installed state. If the reporting route or visibility
is unqualified, keep that gate pending instead of inventing a route or treating
an empty response as success. Publication and assignment GETs cannot substitute
for those reports. A clean-device AMA claim requires a clean-device trial.

## Tenant-wide client AMA

After explicit blast-radius review, use the existing helper. Removal is also a
separately authorized operation with the same receipt-bound identities:

```powershell
pwsh -File ./scripts/Set-ClientAmaScope.ps1 -Action Ensure -AssociationName '<owned-name>' -DcrId '<dcr-resource-id>' -DcrLocation '<location>' -TenantId '<tenant-guid>' -SubscriptionId '<subscription-guid>' -ConfirmTenantWideScope
pwsh -File ./scripts/Set-ClientAmaScope.ps1 -Action Remove -AssociationName '<owned-name>' -DcrId '<dcr-resource-id>' -TenantId '<tenant-guid>' -SubscriptionId '<subscription-guid>' -ConfirmTenantWideScope
```

This helper discovers advertised preview API versions at runtime; they are not
pinned. Preserve sanitized provider metadata and the actual versions used for
monitoredObjects and dataCollectionRuleAssociations. Obtain separate GET
readbacks of the exact monitored object, association and DCR through the selected
ARM context. Record the literal URLs, versions, results and fresh client
Event/Heartbeat proof. The association affects all client-installed AMA devices
in that tenant. Follow the explicit removal settings in operations; an exact
acknowledgment allowing a dangling association is a separate decision, not
cleanup acceptance.

## MDE library lifecycle and separate verification

After authorization, publish or clean up with the existing receipt-bound helper:

```powershell
pwsh -File ./scripts/Publish-LiveResponseScript.ps1 -ScriptPath '<generated-script>' -ExpectedTenantId '<tenant-guid>' -ExpectedAccount '<upn>' -EnvironmentName '<environment>'
pwsh -File ./scripts/Remove-LiveResponseScript.ps1 -StatePath '<private-receipt>'
```

The remover checks before DELETE; it does not perform a post-delete GET. Query
again after publication and cleanup. The example below uses the current cached
CLI identity and the same legacy token audience as the source. Fill the expected
identity and exact receipt filename privately; keep credentials only in memory:

```powershell
$account = az account show --output json --only-show-errors | ConvertFrom-Json
if ($LASTEXITCODE -ne 0 -or $account.tenantId -ine $expectedTenantId -or
    $account.user.name -ine $expectedAccount -or $account.environmentName -ne 'AzureCloud') {
    throw 'Selected Defender account/tenant/cloud mismatch.'
}
$token = az account get-access-token --resource 'https://api.securitycenter.microsoft.com' --tenant $expectedTenantId --query accessToken --output tsv --only-show-errors
if ($LASTEXITCODE -ne 0 -or [string]::IsNullOrWhiteSpace($token)) { throw 'No cached Defender token.' }
try {
    $response = Invoke-RestMethod -Method Get -Uri 'https://api.security.microsoft.com/api/libraryfiles' -Headers @{ Authorization = "Bearer $token" } -ErrorAction Stop
    @($response.value | Where-Object { $_.fileName -eq $receiptFileName }) |
        Select-Object id, fileName, description
} finally {
    Remove-Variable token,response -ErrorAction SilentlyContinue
}
```

Capture sanitized selected-file metadata before/after publication and an
independent successful GET with no selected-file match after deletion. Errors,
wrong identity, incomplete responses and denied visibility are not absence.
Library publication/deletion never runs the file. Keep any device session,
execution, endpoint outcome and Defender timeline claim pending until separately
authorized and observed.

The September record in [validation](validation.md) remains historical. It does
not establish current revision acceptance, clean-device AMA installation,
Azure VM acceptance or final Live Response publication. Repeat affected gates
at the candidate revision. See [operations](operations.md) for rollback limits.
